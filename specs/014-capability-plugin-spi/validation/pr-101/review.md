## PR #106 Sourcery

Four comments (#0 to #4); #3 and #4 are fixed, #0 to #2 declined. Codex follow-up (two P2) on the fixes is recorded at the end of this section.

- **#4 KICK published no committed event (fixed).** Added `EventKind.KICKED`, published by `KickCommandHandler` from the successful `Kicked` branch only, after the membership transition and outside every lock. Subject is the kicked member's presented identity, `before` the channel, `after` the reason, new `CommittedEvent.actor` the kicker's presented identity, audience the pre-removal recipients without the kicked member. KICK is the only removal that reuses `ChannelRegistry.kick`; no other command in core or the bundled extensions removes a member this way. Tests in `CommittedEventTest`: `aKickCarriesTheKickedIdentityTheKickerTheReasonAndThePreRemovalAudience`, `aKickWithoutACommentReportsTheKickersNicknameAsTheReason`, `aRejectedKickPublishesNothing` (non-operator, non-member, absent target, no such channel, missing parameters).
- **#3 No global order across sessions (documented, not changed).** `EventKind`, `CommittedEvent` and `CommittedEvents` Javadoc, the capability-spi contract and data-model.md state the ordering guarantee (narrowed by the Codex follow-up below). Test: `eventsASessionCausesItselfArePublishedInTheOrderItIssuedThem`.
- **#0, #1, #2 (declined).** #0: a hung trusted hook is out of scope per runtime-lifecycle.md. #1: TAGMSG sender negotiation is unchanged from main. #2: AWAY runs only on the session's own connection thread.
- **Codex follow-up P2 1: per-subject order was over-claimed (documentation narrowed, no locking).** A KICK runs on the kicker's thread, so two kicks of one member by different users, or a KICK racing the member's own NICK or JOIN, can publish out of transition order. The guarantee is now: events caused by one session's own commands are published in the order that session issued them; an event another session causes about it (`KICKED`) has no order relative to those, and nothing is ordered across subjects. Narrowed in `EventKind`, `CommittedEvent`, `CommittedEvents`, the contract and data-model.md. The sequential test is renamed to assert only the self-caused events (join, part, join, nick, quit), excluding `KICKED`.
- **Codex follow-up P2 2: the KICKED subject was read late from the mutable session (fixed).** `KickCommandHandler` now resolves the target's presented identity before the transition, outside every lock, when a provider listens for `KICKED` (`CommittedEvents.listensTo`), and passes it into `CommittedEvents.kicked`; if the removed member is not the one found by name beforehand, it falls back to resolving at publication. No hostname or cloak callback runs under a membership lock. Regression test `KickEventIdentityTest.aNickChangeBetweenCommitAndPublicationDoesNotRenameTheKickedSubject` uses a test-only after-commit seam to change the nick between commit and publication; it is synchronous, so it needs no waits or cleanup.
- **Codex follow-up 2, P2 1: the capture used a different name match than the registry (fixed).** `memberNamed` used `equalsIgnoreCase`, so `KICK #c {bob}` removed `[bob]` but captured no identity. It now uses `Channel.findMember`, the same RFC1459 folding the registry uses. Test: `KickEventIdentityTest.anRfc1459EquivalentSpellingOfTheTargetStillCapturesItsIdentity`.
- **Codex follow-up 2, P2 2: the optional capture could abort a KICK (fixed).** A hostname-display extension throwing for the victim, with a `KICKED` listener present, failed the command before the transition. The capture is now contained: on `RuntimeException` the KICK proceeds, the type alone is logged, and (superseded by follow-up 3) the event resolved the identity at publication. Test: `KickEventIdentityTest.aFailingDisplayForTheVictimOnlyNeverAbortsTheKick` (victim host only; the KICK succeeds and is notified, no event, nothing escapes). The kicker's own prefix failure still aborts before the transition, unchanged. `CommittedEvents.kicked` keeps the Sonar S1172 change (no kicker parameter).
- **Codex follow-up 3, P2: the late-resolution fallback reintroduced the rename (fixed).** When the pre-transition capture failed or found no member, `CommittedEvents.kicked` re-resolved the identity from the mutable session at publication, so a transient display failure plus a later NICK named the new nickname. The fallback is gone: `kicked` requires a captured identity, and `KickCommandHandler` skips `KICKED` (the KICK itself proceeds) when none was captured, logging once with the failure type or "target not found by name". This supersedes the fallback described in follow-up 2. Test: `KickEventIdentityTest.aCaptureThatFailsOnceNeverLetsALaterNickChangeNameTheEvent` (display fails on the first victim lookup only, with the after-commit rename seam: the KICK succeeds and no event is published). `aFailingDisplayForTheVictimOnlyNeverAbortsTheKick` still holds.
